# Traces of agent-assisted development

What counts as a trace, and where it must not appear. Does not apply to
repositories that are themselves tools for agents (e.g. `murpiano-dx`).

## 1. Where to check

Everything a repository visitor can see:

- tracked files and their content;
- every commit on published branches and tags: message, trailers, author,
  committer;
- branch and tag names;
- pull requests: title, description, branch;
- releases: title and notes;
- repository description and topics.

## 2. Files

Not tracked and never present in published history. List:
[gitignore-agents](../../global/gitignore-agents).

## 3. Text

Nowhere in the checked area is there any mention of assistants, agents,
models, or generation: assistant and vendor names, `Generated with`,
`Generated by`, `AI-generated`, `as an AI`, `Co-Authored-By` with an assistant
or bot, robot emoji.

Exception: a mention that is part of the product itself (e.g. integration
with a model's API). The owner confirms such a case.

## 4. Author

All authors and committers in published history are the owner, with a single
email: their account's noreply address. For murpiano repositories:
`Bogdan Trotsenko <159007823+murpiano@users.noreply.github.com>`.

- Name — as in the GitHub profile. Older commits may show `murpiano`: same
  email, GitHub displays them as the owner's commits, no need to rewrite.
- Committer `GitHub <noreply@github.com>` on commits made on the site (button
  merge) is normal.
- A real email appearing in history is a finding: GitHub substitutes it on a
  site merge if the account doesn't have "Keep my email addresses private"
  enabled (Settings → Emails). Both that toggle and "Block command line
  pushes that expose my email" have been enabled since 2026-10-17.
- Commits before 2026-10-17 with a real email or a different name are left as
  is: the owner's decision. The scanner will show them as a finding; accept
  it, don't rewrite or offer to rewrite history for the author's sake. The
  standard applies to new commits.

## 5. Messages and branches

- Commit messages, PR and release titles have no emoji and follow the
  repository's convention. If the repository has none of its own, the
  default kysaro preset is used: [rules](https://github.com/murpiano/kysaro#message-format).
- Branches don't start with `claude/`, `copilot/`, `codex/`, `cursor/`,
  `devin/`, `ai/`, `agent/`.

## 6. Prevention

`sync.py` configures connected projects so traces don't appear in the first
place:

- the list from `global/gitignore-agents` is written into `.git/info/exclude`
  for every connected project (`exclude_agent_files`);
- this pre-commit hook is installed in every connected project
  (`install_precommit_hook`), as long as it doesn't already have an unrelated
  hook of its own; it only sees staged files and the diff, not the commit
  message text itself;
- commit-msg is wrapped by the same scanner separately
  (`install_commitmsg_hook`, [commit-msg-hook.sh](commit-msg-hook.sh)) — only
  if a hook already exists there (its own from
  [Kysaro](https://github.com/murpiano/kysaro) or a custom one), never created
  from scratch, so as not to compete with Kysaro's own installation for the
  file; the original hook runs first, then the message text is checked for
  the mentions listed in section 3;
- the git author in a new project with no history is the owner from section 4
  (`sync.py` at `init`); check `attribution` in the agent's own settings
  separately.
- on a project with Husky (`core.hooksPath` points at `.husky/_`) both hooks
  are appended to the tracked `.husky/pre-commit` / `.husky/commit-msg`, not
  to `.husky/_/...` — that directory is regenerated by Husky itself on every
  `npm/pnpm install`, and any edit there silently disappears with no error
  (`hook_target` in `sync.py`).
- the appended line embeds an absolute local path (`ACTIVE_ROOT`), which only
  works on this one machine. The file it's appended to (`.husky/pre-commit` /
  `.husky/commit-msg`) is tracked by git and usually shared across the whole
  team — so the edit must be hidden from the index, otherwise an accidental
  `git add -A`/`commit -a` would ship a path to the repository that breaks
  for any other team member. `mark_skip_worktree` in `sync.py` does this
  right after writing: `git update-index --skip-worktree <file>` — the file
  keeps working on disk, but `git status`/`git add` no longer see it at all.
  The rule is the same whether it's your own project or someone else's (a
  contribution to a colleague's repository) — a machine-local path must never
  be committed, period, not only on a team.

A local hook is not a 100% barrier: it can be missing on a new machine,
bypassed with `--no-verify`, or lost when Husky is reinstalled. The real
barrier is a CI check, committed into the project itself and independent of
the local machine: [templates/agent-trace-check.yml](templates/agent-trace-check.yml),
the same pattern list as above, but over the push/PR's commit range and
diff. Wire it in via `repo-ci` for any project with CI on GitHub Actions, and
make it a required status check in branch protection — otherwise a PR with
a trace can still be merged manually past a red check.

## 7. What can't be removed

GitHub keeps `refs/pull/<n>/head` for every PR with the original commits.
Only GitHub support can delete these. Forks and other people's clones also
retain the old history.

## 8. Secrets

The scanner also looks for secrets: `.env` files (except `.env.example`,
`.env.sample`, `.env.template`), `*.pem`, `*.key`, `id_rsa`, `.npmrc`,
`credentials.json` keys, private keys in text, GitHub/OpenAI/Anthropic/
AWS/Slack/Google tokens, and assignments of the form `token = <long value>`.
The report only shows the path, line, or commit — never the value itself.

- A secret in the working tree: remove it from the file, move it to an
  environment variable, add the file to `.gitignore`.
- A secret in history has already leaked if there was a push. First revoke it
  and issue a new one with the service, then, at the author's discretion,
  clean the history (`--index-filter` or `git filter-repo
  --replace-text`). Cleaning without revoking doesn't help.
- Test or example values the scanner mistook for a secret: the author marks
  them as a false positive.
